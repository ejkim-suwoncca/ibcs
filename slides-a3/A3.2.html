A3.2.1 · Schemas

Three Levels of Schema

A schema describes how a database is organised. The level changes depending on who needs the design.

Conceptual
Big picture.
Entities and relationships only.
Logical
Database design.
Tables, attributes, keys, and data types.
Physical
Implementation.
How the database is stored, indexed, and created.

Exam habit: move from meaning → structure → implementation.

A3.2.2 · ERD Concepts

Cardinality & Modality

Cardinality
Maximum number of related records: 1:1, 1:M, or M:M.
Modality
Minimum number of related records: 0 means optional, 1 means required.
Shopping relationshipCardinalityModality
User places Order1:M
one user, many orders		User can have 0 orders. Each order must have 1 user.
Order contains ProductM:M
many orders, many products		Each order has at least 1 item. A product can be in 0 orders.
Order uses OrderItem1:M
one order, many line items		OrderItem must belong to exactly 1 order and 1 product.

Design choice: ORDER_ITEM resolves the M:M relationship and stores Quantity and UnitPriceAtPurchase.

A3.2.3 · Data Types

Database Data Types

A database type is stricter than a Python type. It controls storage, validation, sorting, and calculations.

TypeUse it forShopping exampleWhy it matters
INTEGERWhole numbersStockQty = 42Math and sorting work correctly.
DECIMAL(p,s)Exact money valuesUnitPrice = 19.99Better than FLOAT for currency; avoids rounding surprises.
REAL / FLOATApproximate decimalsRatingAverage = 4.72Good for measurements, not exact money.
CHAR(n)Fixed-length textCountryCode = KREvery value has the same length.
VARCHAR(n)Variable-length textEmail, ProductNameSaves space when text lengths differ.
DATECalendar datesOrderDate = 2026-09-11Can compare by date, not alphabetically.
TIMETime of dayDeliverySlot = 14:30:00Can validate and sort time values.
BOOLEANTrue or falseIsPaid = TRUEPrevents unclear values like yes / y / paid.

IB warning: Phone numbers and postal codes are usually VARCHAR, not INTEGER, because leading zeros and symbols matter.

A3.2.5 · Normalisation

Normalising a Shopping Order

Normalisation reduces repeated data and keeps updates accurate.

Messy Starting Table
One order row stores user details, product details, and item lists together.

Repeated emails, repeated product names, repeated prices.
Normalised Goal
USERS stores user facts.
ORDERS stores order facts.
PRODUCTS stores product facts.
ORDER_ITEMS stores what was bought.

IB requires: understand 1NF, 2NF, and 3NF using a real scenario.

A3.2.5 · First Normal Form

1NF — One Value per Cell

✗ NOT in 1NF

OrderIDUserEmailProducts
O1001mina@example.comUSB Hub, Keyboard
O1002jun@example.comMouse, Cable, Stand

✓ In 1NF

OrderIDProductIDUserEmailQty
O1001P01mina@example.com1
O1001P02mina@example.com1
O1002P03jun@example.com2

1NF rule: atomic values, no repeating groups, and a primary key.

A3.2.5 · Second Normal Form

2NF — Depend on the Whole Key

Use this when a table has a composite key. In ORDER_ITEMS, the key is OrderID + ProductID.

✗ NOT in 2NF

OrderIDProductIDQtyProductNameUnitPrice
O1001P011USB Hub19.99
O1001P021Keyboard45.00

ProductName and UnitPrice depend only on ProductID.

✓ In 2NF

OrderIDProductIDQtyUnitPriceAtPurchase
O1001P01119.99
ProductIDProductNameCurrentPrice
P01USB Hub19.99
P02Keyboard45.00
A3.2.5 · Third Normal Form

3NF — No Non-Key Dependencies

Transitive dependency: OrderID determines UserID, and UserID determines UserEmail.

✗ NOT in 3NF

OrderIDUserIDUserEmailOrderDate
O1001U01mina@example.com2026-09-11
O1002U01mina@example.com2026-09-12

UserEmail belongs to USERS, not ORDERS.

✓ In 3NF

OrderIDUserIDOrderDate
O1001U012026-09-11
UserIDNameEmail
U01Minamina@example.com
Summary · Normal Forms

Shopping Table Checklist

Normal FormQuestion to askShopping fix
1NFDoes each cell hold one value?Split product lists into separate order-item rows.
2NFDoes every non-key field depend on the whole composite key?Move ProductName and CurrentPrice to PRODUCT.
3NFDoes any non-key field depend on another non-key field?Move UserEmail to USERS, not ORDERS.

Memory line: the key, the whole key, and nothing but the key.

A3.2.7 · Denormalisation

When to Denormalise?

Sometimes we repeat data on purpose to make read-heavy pages faster.

Useful Example
A product analytics dashboard stores ProductName and CategoryName beside each sales row.

Fewer joins, faster reports.
Trade-Off
Repeated data can become inconsistent.

If a product name changes, every copied value must be updated.

Use it for: reporting and analytics. Avoid it for live order processing where accuracy matters most.

Common Errors

Common Mistakes

✗
Confusing modality and cardinality — Cardinality = how many (max). Modality = whether it's required (min: 0 or 1).
✗
Thinking 2NF applies to all tables — 2NF only matters with composite primary keys. If PK is a single column, 1NF already implies 2NF.
✗
Stating normalisation benefits generically — always link to the scenario. "ProductName is stored once in PRODUCTS, not repeated in every order item."
✗
Using the wrong data type — Phone numbers look like integers but should be VARCHAR (leading zeros, formatting symbols). Match data types to real-world meaning.

Key Takeaways

Schemas
Conceptual — USER, ORDER, PRODUCT and their relationships
Logical — USERS, ORDERS, PRODUCTS, ORDER_ITEMS tables
Physical — spreadsheet tabs or DBMS tables with validation/indexes
ERDs
Shopping ERD uses USERS, ORDERS, ORDER_ITEMS, PRODUCTS
Cardinality = max (1:1, 1:M, M:M)
Modality = min (0=optional, 1=mandatory)
Normal Forms
1NF — one product per order-item row
2NF — product facts move to PRODUCTS
3NF — user facts move to USERS
"The key, the whole key, nothing but the key"
Denormalisation
Intentional redundancy for read performance
Product reports may copy names/categories
Live orders should stay normalised
